## How to read this document

Each entry lists: what it is, how it actually works, where it plugs into Pandora, and the specific way it can fail or be misapplied — every component here survived a ruthless-critic pass, but "survived" means *scoped correctly*, not *flawless*. Treat the Limitation/Risk column as a condition of use, not a footnote.

## 1. Security & Isolation Core

The load-bearing layer. This is the actual answer to the CPU-zone/GPU-zone isolation thesis: CPU zone holds all execution authority, GPU zone (and any external hardware) can only propose.

| ID | Component | Rating | Description | Working Mechanism | Kernel Integration Point | Limitation / Risk |
|---|---|---|---|---|---|---|
| SEC-01 | **Sentinel Gate Credential Separation** | 10/10 | CPU-zone is the sole holder of execution credentials; GPU-zone / accelerators can submit proposals but never hold authority to execute privileged ops directly. | Adapted from Pandemonium's Sentinel Gate: a hard credential boundary, not a policy suggestion — GPU-zone requests are structurally incapable of self-authorizing. | The literal thesis of the CPU/GPU isolation model — every privileged dispatch routes through this gate. | Adds latency if applied to every dispatch indiscriminately — must scope to Ring-2-equivalent (privileged) ops only, not bulk/Ring-0 traffic. |
| SEC-02 | **Ring 0–3 Privilege Classification** | 9/10 | Every operation is assigned a privilege ring, recomputed fresh at each dispatch — never discounted or inherited from prior benign history. | Ring level is a pure function of the current action's properties, not a running trust score. | Governs which ops need Sentinel Gate approval vs. run unchecked. | 4-tier granularity is coarse for fine-grained DMA/memory permissions — needs sub-ring extension for real hardware diversity. |
| SEC-03 | **Tempered Trail** (decay + velocity + cross-category firewall) | 9/10 | Prevents a component from earning elevated trust purely through a long streak of benign use. | Combines a decaying trust window, a velocity cap on trust-gain rate, and a firewall stopping trust gained in one category from leaking into another. | Applied to GPU-zone: repeated benign dispatches never quietly earn expanded privilege. | A sufficiently patient, slow adversary staying under all thresholds simultaneously remains an open problem — industry-wide, not unique to this design. |
| SEC-04 | **Uncertainty-Aware Tool Trust → `admit` Airlock Gate** | 8/10 | Single, typed, mandatory seam through which all untrusted external/hardware input must pass before being treated as safe. | Raw hardware/DMA data enters as a `Tainted<T>` type; only the `admit` function can convert it to a trusted `Scalar<lo,hi>` — no other code path may bypass it. | Every raw hardware read (USB, sensor, DMA descriptor) in the kernel. | Occasional false-flagging of benign bursts — threshold needs empirical tuning per device class. |
| SEC-05 | **Epoch-Fenced Capability Validity** | 10/10 | Closes the exact TOCTOU (time-of-check-to-time-of-use) race the `admit` gate alone can't fully close. | A global monotonic epoch counter; every capability carries the epoch it was validated in, and dispatch-time re-checks the epoch still matches before execution. Formally provable (TLA+ precedent). | Wraps every capability check between validation and actual dispatch. | Guarantee only holds if the formal proof is actually re-derived for Pandora's specific hardware/timing model, not assumed by analogy. |
| SEC-06 | **CBAC — Ephemeral Time-Boxed Capability Tokens** | 9/10 | Capabilities expire, not just scope — extends static capability addressing with a decay dimension. | Every issued capability carries a validity window; past expiry it's structurally unusable regardless of whether it was "revoked." | Layered on top of SEC-11 (capability addressing) for anything privileged and long-lived. | Expiry-check overhead on every high-frequency call — must stay cheap (pairs with SEC-13, symmetric MAC). |
| SEC-07 | **Sub-Agent Epoch Inheritance** | 8/10 | Child processes/threads inherit their parent's epoch and can be revoked in cascade without per-child bookkeeping. | Revocation of a parent epoch instantly invalidates all descendants sharing it — O(1) revoke, not O(children). | Process/thread spawn and teardown paths. | Inheritance chain itself is new state — implementation must guarantee O(1) revoke, not O(depth), or the win disappears. |
| SEC-08 | **SRAM Tombstone List + Bounded Garbage Collection** | 9/10 | Fast, on-chip, fail-closed check for revoked capabilities before any dispatch proceeds. | A Bloom-filter-backed revocation list held in fast on-chip memory, epoch-scoped eviction to keep it bounded. | Pre-dispatch check, sits directly in front of SEC-01. | Unbounded false-positive creep if GC eviction isn't strictly epoch-scoped. |
| SEC-09 | **seL4-Style Capability Addressing** | 8/10 | Every resource access is an unforgeable capability, not an ACL lookup — the strongest formally-precedented "fully secure" claim currently available. | Capabilities are first-class, unforgeable tokens; possession *is* authorization, eliminating a whole class of confused-deputy and ACL-drift bugs. | Foundational addressing model for the kernel's whole resource-access layer. | Real performance overhead vs. raw pointer access; formal verification is genuine engineering cost, not a free upgrade. |
| SEC-10 | **Enclave-Local Sync MAC vs. Provisional Execution Lock** | 9/10 | Concrete execution split matching the CPU/GPU isolation model: CPU-zone ops get a hard, sub-microsecond synchronous guarantee; GPU/remote-zone ops get an async, reversible hold + compensator instead. | CPU-zone: synchronous MAC-verified execution lock, blocking. GPU/remote-zone: provisional hold that can be rolled back if verification later fails. | Defines exactly how the CPU/GPU trust boundary executes, not just how it's declared. | The remote/GPU path never gets the sub-µs guarantee — this is an honest, permanent trade-off, not a bug to fix later. |
| SEC-11 | **Symmetric MAC for High-Frequency Checks** | 7/10 | Avoids per-call asymmetric-crypto latency on the hot capability-check path. | Symmetric MAC verification instead of public-key crypto wherever check frequency is high and the trust anchor is already established. | Hot-path pairing with SEC-06/SEC-08. | Weaker than asymmetric crypto if the symmetric key distribution itself is ever compromised — key-management dependency, not eliminated. |
| SEC-12 | **Hardware Root-of-Trust Sidecar** | 8/10 | Ensures a compromised host OS/kernel can't silently disable its own security layer. | TPM/TEE attestation required before the sidecar will issue any capability at all — the check exists outside the thing it's checking. | Boot-time and periodic re-attestation gate for the whole capability-issuance pipeline. | Attestation infrastructure is real, non-trivial engineering cost — not a drop-in. |
| SEC-13 | **Constraint-Checked Decomposition** | 8/10 | Pre-dispatch feasibility check before any task is "dismantled" and sent to GPU-zone as sub-entities. | Verifies the decomposed task graph is structurally feasible (dependencies resolvable, no orphaned sub-tasks) before commit. | Sits in front of any bundle→sub-entity dispatch to GPU-zone. | Checks feasibility, not cumulative risk — must pair with a risk-ledger mechanism (see FLT-02-adjacent Cumulus-style tracking) or salami-slicing risk reopens. |
| SEC-14 | **Disjoint Backup Pre-Compute** | 8/10 | Mandatory rollback plan computed *before* any irreversible memory/DMA operation is allowed to fire. | No irreversible op executes without a pre-validated inverse/backup already staged. | Gate in front of memory-remap, dealloc, and irreversible DMA writes. | Roughly doubles the cost of the operation it protects — must be scoped strictly to genuinely irreversible ops, not bulk/reversible traffic. |
| SEC-15 | **Tool Tiering (A/B/C) + Wake Log + Irrevocable Waypoint** | 9/10 | Classifies every device/driver operation into Contained / Compensable / Witnessed-Irreversible, with an append-only audit ledger for the last tier. | Tier A (contained, freely retryable), Tier B (compensable, has a defined undo), Tier C (irrevocable — logged to an append-only Wake Log before it fires). | Extends SEC-14 into a full concrete taxonomy for every driver-facing operation, not just memory ops. | Unregistered/new devices default safely to Tier C, but that adds classification overhead on every new integration. |

## 2. Verification, Audit & Build-Mode Hardening

Proves the security layer's claims are actually true on real silicon, not just true on paper.

| ID | Component | Rating | Description | Working Mechanism | Kernel Integration Point | Limitation / Risk |
|---|---|---|---|---|---|---|
| VER-01 | **Oblivious Compare-Exchange** | 9/10 | The branchless, always-write-select primitive the `admit` gate's arithmetic actually needs to be genuinely constant-time. | Both branches of a comparison are always computed and selected via a data-independent move — no conditional branch exists to time. | Core primitive inside SEC-04's `admit` gate and any other constant-time check. | Only as constant-time as the compiled `cmov` actually is on target silicon — unverified without VER-02. |
| VER-02 | **dudect / Welch's-t Constant-Time Verification Harness** | 8/10 | CI-gate proof that the kernel's branchless primitives are actually constant-time on the real compiled binary, not just in source. | Statistical timing-distribution comparison (Welch's t-test) between secret-dependent execution paths, run continuously in CI. | Gates every release of any component claiming constant-time behavior (VER-01, SEC-04, SEC-10). | Statistical, not formal proof — must be rerun on every silicon revision and compiler update, ongoing cost not one-time. |
| VER-03 | **Secure / Turbo Dual-Compile Split** | 9/10 (2 independent convergences: kernel-level + GPU-specific Verplaca instance) | Two build modes — Secure (fully verified, oblivious paths) and Turbo (adaptive, speed-optimized) — compiled separately and never sharing a runtime path. | Compile-time split, not a runtime flag — eliminates any chance of the two modes' code accidentally mixing. | Applies at the whole-kernel level and, independently validated, at the GPU-dispatch level (Verplaca-Secure uses Beneš/Waksman oblivious permutation networks + dudect validation; Verplaca-Turbo uses warp-vote convergence checks). | Roughly doubles binary maintenance surface — one shared code path anywhere collapses the entire guarantee. |
| VER-04 | **In-Kernel Warp-Vote Verification** | 8/10 | Verifies speculative GPU-zone work without a round-trip to the CPU host. | Verification happens via in-kernel warp-vote consensus on the GPU itself, avoiding the host round-trip that dominates latency in naive designs. | Any speculative/fast-path GPU dispatch that needs correctness confirmation before its result is trusted. | Still costs real in-kernel cycles — cheaper than a host round-trip, not free. |
| VER-05 | **Idempotency Keys on Retry/Compensation** | 7/10 | Makes driver-restart and retry logic safe against double-execution. | Every retryable operation carries a unique idempotency key; a retried call with the same key is a no-op if already applied. | Pairs with the driver-restart mechanism (isolated, restartable driver shell) so restarts can't double-fire an operation. | Requires every retryable kernel-facing op to expose an idempotency key — real, non-trivial API surface cost. |
| VER-06 | **Decision-Table Over Trained Model (for control decisions)** | 7/10 | Design philosophy: deterministic lookup tables for security/control decisions, never a trained classifier. | "A model costs more than the kernels it's choosing between" — kept explicit and auditable rather than opaque. | Applies wherever Pandora makes a security- or control-relevant dispatch decision. | Not a component so much as a standing constraint — real value is in refusing ML shortcuts elsewhere in the design. |

## 3. Fault Handling & Escalation

Replaces binary crash/continue with graded, terminating responses.

| ID | Component | Rating | Description | Working Mechanism | Kernel Integration Point | Limitation / Risk |
|---|---|---|---|---|---|---|
| FLT-01 | **Three-Zone (Green/Yellow/Red) Fault Triage** | 8/10 | Graded fault response instead of binary crash/continue. | Green = continue normally, Yellow = correctable in-place, Red = terminate/isolate. Independently converged on by two unrelated source documents. | Driver-fault handling layer, replacing the bare restart-only model. | "Yellow" in-place correction needs its own correctness proof per distinct fault class — not automatically safe by category alone. |
| FLT-02 | **Arbiter Ladder** | 8/10 | Structured, terminating escalation path for unresolved conflicts/faults instead of an undefined hang. | Retry with a structurally distinct strategy → escalate to a genuinely distinct fallback mechanism → human/timeout → default to the most conservative disputed option, with the disagreement surfaced explicitly. | Driver-crash recovery and any deadlocked internal negotiation (e.g. CPU/GPU zone resource contention). | Terminates in "flagged unresolved," not guaranteed recovery — honest limit, not a full fix. |
| FLT-03 | **Confidence-Gated Steering** | 7/10 | Upgrades every binary correction trigger elsewhere in the registry (e.g. SEC-03's trust throttling) to a proportional response scaled by confidence, instead of a hard on/off snap. | Intervention strength scales continuously with how far a metric is over threshold, rather than jumping straight to full lockdown. | Retrofit layer over Tempered Trail, Cadence-style throttling, and Herald-style rate-limiting. | Requires a well-defined continuous confidence signal per mechanism it's applied to — doesn't exist yet for most; this is a retrofit target, not a drop-in. |

## 4. Scheduling & Dispatch

Governs *when* and *how* work is assigned — this is where most of the actual "speed" claim lives, per the TimSort principle: the primitives below are mostly known, the value is in the decision layer governing their use.

| ID | Component | Rating | Description | Working Mechanism | Kernel Integration Point | Limitation / Risk |
|---|---|---|---|---|---|---|
| SCH-01 | **Static Compile-Time Graph-Coloring Scheduler** | 8/10 | Zero-runtime-overhead resource assignment for fixed-shape workloads. | Resource conflicts are resolved once, at compile time, via graph coloring — no scheduler decision happens at runtime for these paths. | DMA-channel binding and any other fixed-shape resource assignment. | Only works for fixed-shape workloads — not a substitute for the general dynamic process scheduler. |
| SCH-02 | **Bitonic Sorting Network (Batcher)** | 8/10 | Branchless, GPU-native, fixed-schedule parallel sort — matches the "dismantle bundle into entities" dispatch concept directly. | Fixed compare-exchange network, oblivious to data content, fully parallelizable on SIMT hardware. | GPU-zone dispatch/memory-queue sorting. | Requires power-of-2 padding, wasting cycles on non-power-of-2 batch sizes — scope to the GPU queue subsystem only. |
| SCH-03 | **Calendar Queue Sort** | 7/10 | O(1)-average insert/extract task/interrupt priority queue — real, precedented OS scheduler primitive. | Bucket-indexed queue keyed by time/priority, avoiding full sort on every insert. | Interrupt and task-priority scheduling. | Worst-case degrades badly under adversarial burst clustering — a real DoS vector if bucket boundaries are predictable. |
| SCH-04 | **Cycle Sort** | 6/10 | Minimum-write sorting, purpose-built for flash/NVM wear-leveling, not general use. | Achieves theoretically minimal number of memory writes for a given permutation. | Kernel's persistent/flash memory manager, wear-leveling path only. | O(n²) in the general case — a performance trap if used outside its narrow niche. |
| SCH-05 | **EEVDF-Class Deadline Scheduler** | 8/10 | Current real-world state of the art (Linux 6.6+) for fairness-vs-latency trade-off in process scheduling. | Earliest-Eligible-Virtual-Deadline-First — schedules based on virtual deadlines rather than pure fairness accounting, improving tail latency. | Pandora's general-purpose CPU process scheduler. | Tuning complexity remains real; it's a strong heuristic, not a provably optimal scheduler. |
| SCH-06 | **Decision-Table Dispatcher + Online Miss-Rate Auto-Disable** | 8/10 | The core TimSort-shaped component: a deterministic table routes work to the right specialized path, and any speculative path that starts losing more than it wins gets auto-disabled online. | Cheap signature extraction (size, sortedness, skew shape, etc.) → table lookup → in-kernel verification → running miss-rate tracked per path, disabling it if it stops paying off. | The general dispatch layer governing which specialized execution path (of many in this registry) handles a given workload. | The decision table itself needs maintenance as real workload shapes drift over time — not "set and forget." |
| SCH-07 | **PSRS Bucketing (Parallel Sorted Redistribution Sort)** | 8/10 | Proven (measured, not theoretical) large win for redistributing/bucketing skewed data before dispatch. | Samples data, computes splitters, redistributes into balanced buckets before parallel sort/dispatch — validated ~5 orders of magnitude win over naive histogramming on skewed data. | GPU-zone task/token redistribution before dispatch (e.g. MoE-style routing). | Only wins where data is genuinely skewed — dead weight against a vendor sort on uniform load. |
| SCH-08 | **Skew-Shape Classifier** | 7/10 | Distinguishes *discrete duplicate-mass* skew from *continuous* skew so the dispatcher routes to the correct specialized path. | Cheap sampled-skew-shape check feeding into SCH-06's decision table. | Immediately upstream of SCH-07 and any continuous-skew fast path. | Adds a classification step to every dispatch — must stay cheap or it eats the win it's meant to unlock. |
| SCH-09 | **AD\* (Anytime Dynamic A\*) Time-Boxing Wrapper** | 7/10 | "Best answer by deadline X, keep refining if more budget is granted" — real fit for soft-real-time kernel scheduling. | Anytime algorithm: produces a usable result early, improves it if given more time, replans dynamically as conditions change. | Soft-deadline scheduling contexts where a bounded-but-improvable answer beats an all-or-nothing one. | Correctness under preemption needs its own proof — can't be assumed safe by analogy to the offline case. |
| SCH-10 | **Skip-Gate (asymmetric-payoff precheck)** | 6/10 — *reinforcement, not net-new* | Cheap precheck before an expensive operation, skipping it entirely on a hit. | E.g. a cheap sortedness/already-partitioned check before calling a full sort — a miss costs only the check, a hit saves the entire operation. | General pattern applied wherever a cheap precondition check can avoid expensive work entirely. | Independently converged from two source documents (Cadence-style timing countermeasure, Verplaca's skip-gate) — real technique, but adds nothing new beyond confirming the pattern is sound. |
| SCH-11 | **Formal Oversampling Bound** | 6/10 | Replaces empirical-only splitter-quality tuning with a provable statistical guarantee. | Oversampling ratio derived formally (scaling with `ln(P)`) instead of a fixed, empirically-chosen sample size. | Any sample-based splitter/bucketing step (pairs with SCH-07). | Narrow scope — fixes one specific claim (splitter quality), not a general-purpose technique. |

## 5. Memory Management

| ID | Component | Rating | Description | Working Mechanism | Kernel Integration Point | Limitation / Risk |
|---|---|---|---|---|---|---|
| MEM-01 | **RCU (Read-Copy-Update)** | 8/10 | Lock-free reads with near-zero reader contention — proven, load-bearing Linux-core mechanism. | Readers access data without locking; writers create a new copy and atomically swap the pointer, reclaiming the old copy only after all readers have finished (grace period). | Core primitive for Pandora's "absolute smoothness" claim on any read-heavy shared kernel structure. | Writer-side reclamation logic and grace-period tuning are genuinely non-trivial to get right. |
| MEM-02 | **io_uring-Style Async Ring Buffers** | 8/10 | Batched, near-zero-syscall-overhead async I/O submission/completion. | Shared submission/completion ring buffers between kernel and userspace, batching many operations per syscall instead of one syscall per operation. | Pandora's general async I/O layer. | Larger attack surface if the ring memory is shared with userspace — must be capability-gated (pairs with SEC-09), not left as a raw shared mapping. |
| MEM-03 | **Paged / Radix-Indexed Copy-on-Write Checkpointing** | 10/10 | Effectively a correct, provenanced CoW page manager with a radix-tree page table — directly reusable as Pandora's memory manager. | Blocks are copy-on-write at page granularity, indexed via a radix tree, with reference-counted shared blocks; "checkpoint" is a pointer reset, not a copy. | Core process fork/snapshot/checkpoint-restore mechanism. | Degrades to full recompute/copy under heavy eviction pressure — a real, honestly-stated boundary, not solved by the design alone. |
| MEM-04 | **Dual-Channel State Split** | 8/10 | Core architectural discipline: cheap bookkeeping/metadata state is never conflated with expensive execution/data-plane state. | Physically separate storage and code paths for control-plane metadata vs. data-plane content. | Applies throughout the memory manager and scheduler — e.g. page-table metadata is never stored or moved alongside actual page contents. | It's a discipline, not a mechanism — the real work is enforcing it doesn't leak at every implementation layer, forever. |

## 6. GPU-Zone Execution Layer

The concrete, partially-validated answer to "GPU dismantles tasks" — scoped correctly this time: **wrap and orchestrate proven vendor primitives, don't try to out-algorithm them.**

| ID | Component | Rating | Description | Working Mechanism | Kernel Integration Point | Limitation / Risk |
|---|---|---|---|---|---|---|
| GPU-01 | **Envelope Strategy** | 9/10 | The core dispatch philosophy for this whole layer: don't try to beat vendor GPU kernels algorithmically — reduce how often they're called, how expensive each call is, and how well-conditioned the input is. | Three independent, compounding levers: call-count reduction, call-cost reduction, input-conditioning improvement — none require rewriting the vendor kernel's internals. | Governs the entire GPU-zone accelerator layer's design approach. | The performance ceiling is inherited from the vendor kernel being wrapped, never raised above it — this layer wins on economics, not on raw algorithmic superiority. |
| GPU-02 | **CUDA Graph Capture** | 9/10 | Amortizes host-side launch overhead across repeated calls on similarly-shaped data. | The launch sequence is captured once into a graph and replayed, skipping repeated launch-setup cost. | Kernel's bulk GPU dispatch (mem-scrub, crypto, checksum) where the call shape repeats. | Only pays off if the call shape is genuinely stable and repeated — no benefit for one-off dispatches. |
| GPU-03 | **Multi-Stream Pipelining** | 9/10 | The literal mechanism behind "dismantle a bundle into many entities and execute at once." | Independent GPU calls issued on separate streams let the GPU scheduler overlap them automatically, instead of serializing via a host-side loop. | Any workload genuinely decomposable into independent sub-tasks. | Only wins if the subtasks are *actually* independent — false independence introduces races. |
| GPU-04 | **Vectorized / Coalesced I/O (int4/float4 loads)** | 8/10 | Closes part of the measured sequential-vs-random memory bandwidth gap without any learned component. | Replaces scalar 32-bit gather/scatter with 128-bit vectorized loads wherever alignment permits. | Feeds into/out of any GPU-zone bulk operation (mem-scrub, crypto, checksum). | Alignment-dependent, and offers no benefit at all to scalar/branchy code paths. |
| GPU-05 | **Verplaca-Secure / Turbo GPU Dual-Mode** | — *(reinforcement of VER-03)* | GPU-specific instantiation of the Secure/Turbo split: Secure uses oblivious Beneš/Waksman permutation networks with dudect validation, Turbo uses warp-vote convergence checks with branchless per-warp skip. | Same compile-time, never-merged-at-runtime discipline as VER-03, independently re-derived for the GPU dispatch context. | GPU-zone build-mode split. | Same cost as VER-03 — doubled maintenance surface; listed here as corroboration, not a separate deliverable. |

## 7. Summary & Standing Notes

- **Highest-confidence spine:** SEC-01, SEC-05, SEC-09, MEM-03, GPU-01/02/03 — these are either formally provable, directly precedented in shipping systems (Linux, seL4), or measured (not theoretical).
- **Convergence signal:** FLT-01, VER-03/GPU-05, and SCH-10 each arrived independently from unrelated source documents landing on the same mechanism — treated as a confidence booster, not counted as separate net-new components.
- **Explicitly not solved by anything in this registry:** a sufficiently patient, low-and-slow adversary staying under every detection threshold simultaneously (SEC-03's open limitation); single-source poisoning where no independent corroborating source exists; GPU-zone's fundamentally worse worst-case launch/wake latency for interrupt-class, low-N, branchy work — this registry deliberately does **not** attempt to route that class of work to GPU-zone at all.
- **Standing discipline:** every component above was evaluated against the working "no hidden control flow, no hidden allocation, fail-safe default" invariants before inclusion — components that passed only by redefining those terms were rejected, not rescued.

*End of registry — v1.*
